# ADR-001: JWT Authentication

## Decision
Use JWT (HMAC-signed) tokens for stateless authentication of API requests.

## Status
Accepted (implemented)

## Context
The API needs a stateless authentication mechanism suitable for web and mobile clients.

## Decision
Use JWT tokens generated by JwtService, signed with an HMAC secret stored in configuration (milkweb.jwt.secret). Tokens include userId, phone, and role claims and have an expiration time.

## Why We Chose It
- Stateless tokens work well for REST APIs and mobile clients.
- Simple to validate on each request with the shared secret.

## Alternatives Considered
- Server-side session storage (stateful): would require session store and is less suitable for mobile.
- OAuth2/OIDC: more complex; can be considered later for federation.

## Advantages
- Scales without centralized session store.
- Easy for mobile apps to store and present tokens.

## Disadvantages / Trade-offs
- Token revocation is non-trivial (no built-in server-side revoke).
- Secret management is crucial.

## Security Implications
- JWT secret must be kept secure (env vars / vault). Use short expiry or refresh tokens for greater security.

## Performance Implications
- Token validation is computationally cheap; no DB lookup required for each request (except to rehydrate a user if needed).

## Future Implications
- Consider refresh token design & revocation strategy if fine-grained session control is needed.

## Interview Takeaway
JWTs are appropriate for stateless REST APIs and mobile clients, but plan for revocation/rotation if long-lived sessions are used.
